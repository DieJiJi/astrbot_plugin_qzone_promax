# astrbot_plugin_qzone_promax · QQ动态ProMax

> 给 [AstrBot](https://github.com/AstrBotDevs/AstrBot) 用的 QQ 空间插件。
> 在原版 `astrbot_plugin_qzone` 的核心层之上重做，把「评论」和「发动态」合并成一个插件，
> 并加了**防烧钱的限流闸门**——每一档频次都能在后台自己调。

---

## 为什么会有这个项目

原版插件有个很别扭的体验：

> 你对 bot 说「去评论那条说说，就说『这条我看了三遍』」
> bot 满口答应："好的，我去评论～"
> 结果发到 QQ 空间上的是它自己现编的另外一句。

查源码能看明白原因 —— 原版对外暴露的 LLM 工具签名是这样的：

```python
async def llm_view_feed(self, event, user_id, pos, like, reply)
```

**里面根本没有 `text` 这个参数。** 评论内容是在 `PostService.comment_posts()` 内部直接调
`self.llm.generate_comment(post)` 现编的，对话里你说的话传不进去。

这不是操作问题，是插件设计上的缺口。既然改一改就能用，那就顺手把另外两个也一起做了。

## 四个新功能

### 1️⃣ 指定内容评论 —— 你说什么，它就发什么

`llm_comment_feed` 工具新增 `text` 参数，主人明确说了要评论什么，**必须原样传入**，
不许自作主张改写。同时 `PostService.comment_posts()` 也加了 `text` 形参：传了就照发，没传才让 AI 自己写。

```text
评论说说 0 这条我看了三遍
```

### 2️⃣ 智能评论 —— 带上下文，说人话

评论前会把这三样一起喂给 LLM：

- 说说正文 + 转发内容
- 图片数量
- 已有评论（最近 5 条）

并明确要求「不要和已有评论重复」，避免出现一圈机器人排在下面说同一句客套话。
LLM 调用失败会自动回退到插件自带的生成逻辑，不会直接报错中断。

### 3️⃣ 楼中楼自主回复 —— 别人回你，她自己接回去

后台定时巡检，找出该接话的地方，生成并发出楼中楼回复。

会接的三种情况：

| 场景 | 默认 | 受哪个开关管 |
|---|---|---|
| 别人回复了**她的评论**（在任何人说说下） | ✅ 总是接 | —— |
| 别人在**她自己的说说**下直接评论 | ✅ 默认接 | `reply_own_post_comments` |
| 别人在别人的说说下互相聊天 | ❌ 不插嘴 | —— |

### 🪟 事件驱动巡检窗口 —— 没动静就不敲门

传统做法是「每隔 X 分钟把所有人的空间拉一遍」，哪怕三天没人发动态，接口照样在刷——
这既浪费请求，又容易把号刷进风控（作者本人的号就因此被腾讯踢下线过一次）。

所以这里换成了**事件驱动 + 限时窗口**：

```
平时（无窗口）：  每轮只做 1 次轻量嗅探（看看名单里的人有没有发新动态）
                  ↓ 发现新动态
开窗：           这条动态进入巡检名单，开始盯它
窗口内：         只对窗口内的说说查详情、接楼中楼
窗口关闭：       撑到时限自动过期，从此不再碰这条的接口
```

三种开窗时机：

| 触发 | 说明 |
|---|---|
| 她自己发了动态 | 发布成功那一刻自动开窗 |
| 她评论了某条说说 | 立刻开窗盯这条 |
| 名单里的人发了新动态 | 轻量嗅探发现后开窗 |

两个开关：

| 配置 | 默认 | 作用 |
|---|---|---|
| `watch_ttl_days` | 3 | 窗口存活天数，到期自动关闭 |
| `watch_qqs` | 空 | 要嗅探谁的新动态（QQ 号，逗号分隔）。**主人默认已在名单内**，不用重复填 |

调用量对比（平静日几乎归零，这是防风控的关键）：

| | 老做法（全量轮询） | 事件驱动窗口 |
|---|---|---|
| 每轮基础请求 | 自己说说全量拉取 + 若干条外部详情 | **1 次**轻嗅探 |
| 有互动时 | 同上 | 窗口内逐条（通常 1~3 条） |
| 无人发动态的日子 | 照常全量 | 近乎为零 |

- 扫描范围 = **窗口内的说说**（自己发的、她评论过的、名单里的人新发的）
- `_replied` 集合 + 落盘去重，同一个人对同一条评论**绝不回第二次**
- 已回复记录持久化到 `pro_state.json`，重启不丢
- 冷启动时会补一次：把重启前发的、仍在窗口期内的动态纳入巡检

### 4️⃣ 发动态 —— 手动发、也能定时发

原版插件的 `AutoPublish` 类一直躺在 `core/scheduler.py` 里，但 `main.py` **连 `scheduler` 都没 import**，
也就是说定时发说说从来没生效过。ProMax 把它接了出来，并补上手动入口：

| 入口 | 说明 |
|---|---|
| 命令 `发说说 [主题]` | 按主题生成并发一条；不带主题则由她自己挑话题 |
| 命令 `发原话 <内容>` | 按你给的原话原封不动发，一个字都不改 |
| 命令 `删说说 [序号]` | 删掉自己第 N 条说说，默认最新一条 |
| LLM 工具 `llm_publish_feed` | 你说「发个说说」时她可以自己调用 |
| 定时自动发布 | 配置里打开 `auto_enabled` 才会启动，**默认关闭** |

素材来源三选一（`topic_source`）：

- `chat` —— 从群里聊天记录里提炼主题（原版行为）
- `topic` —— 她自己随便想一个主题
- `news` —— 刷当天科技/AI 新闻，挑一件说看法

## 💰 省钱：四道闸门

自动回复是要调 LLM 的，放着不管一个月能吃掉不少 token。所以额度是**默认就开着的**，不是可选项。

| 配置项 | 默认值 | 作用 | 省什么 |
|---|---|---|---|
| `daily_reply_limit` | 20 | 每天最多自动回复多少条，**0 点自动重置** | 总闸，到期当天彻底停手 |
| `per_user_daily_limit` | 3 | 同一个人每天最多回几条 | 防止某个人跟她聊起来没完 |
| `max_replies_per_round` | 3 | 单轮巡检最多回几条 | 防止一次性爆发式调用 |
| `max_comment_len` | 40 | 每条回复最多几个字 | 字数 = 输出 token，最细粒度 |
| `reply_cooldown_min` | 30 | 两次回复之间冷却（分钟） | 最直接的时间闸 |
| `poll_interval_min` | 10 | 巡检间隔（分钟） | 巡检不调 LLM，只花网络请求 |
| `reply_own_post_comments` | true | 要不要回别人在自己说说下的评论 | 关掉后只处理「别人回她」的场景 |

**「回复多少人就停手」是三个旋钮叠加的结果**：单轮上限 × 冷却 × 每日总额，
任意一个顶到就停。`楼中楼状态` 命令里有一条进度条，一眼能看出今天烧了多少。

**关键设计：配额检查在调 LLM 之前。** 某人今天的额度用完了，直接跳过，**一次 LLM 都不调**，
而不是生成完了再扔掉。

### 回复策略（四档，配置里自由选）

| 值 | 说明 |
|---|---|
| `off` | 关闭，完全不自动回复 |
| `owner_only` | 只回复主人（需要填 `owner_qq`） |
| `friends` | **推荐**：回复所有回复了你的人，遵守全部限流 |
| `everyone` | 激进：冷却减半、单轮上限翻倍。**有 QQ 风控风险，慎用** |

## 命令

| 命令 | 权限 | 说明 |
|---|---|---|
| `发说说 [主题]` | 管理员 | 按主题生成并发一条动态，不带主题则她自己挑 |
| `发原话 <内容>` | 管理员 | 按你的原话原封不动发 |
| `删说说 [序号]` | 管理员 | 删掉自己第 N 条说说，默认最新一条 |
| `评论说说 <序号> <内容>` | 管理员 | 按你指定的原话评论 |
| `智能评论 <序号>` | 管理员 | 结合上下文自动生成评论 |
| `楼中楼` | 管理员 | 立刻巡检并回复一次 |
| `楼中楼状态` | 管理员 | 查看今日额度进度条、冷却、策略 |
| `动态配置` | 管理员 | 查看发动态与楼中楼的当前设置 |

LLM 工具（bot 可自主调用）：

- `llm_publish_feed(text, topic)` —— 发一条**动态**，`text` 有值就原样发
- `llm_comment_feed(user_id, pos, text, like)` —— 评论**好友**的说说，`text` 有值就原样发
  - `user_id` 支持 **QQ 号或好友昵称/备注**（填昵称会用 `get_friend_list` 自动匹配）
  - **留空不再静默回退到动态流**，直接返回参数错误，逼 LLM 回去问主人
- `llm_comment_my_feed(pos, text, like)` —— 评论**机器人自己**的说说（主人说「我的动态」走这个）
- `llm_reply_pending()` —— 检查并处理别人给你的回复

> 两个评论工具是刻意拆开的：原版只有一个工具且 `user_id` 可留空，结果主人说
> 「发到我的动态下」时 LLM 留空 → 落到好友动态流 → 评论到别人头上了。
> 拆开后工具名即语义，另加三层保险：
> 1. `my_feed` 拿到的说说作者不是机器人自己 → 罢手不评
> 2. `feed` 拿到的说说作者就是机器人自己 → 罢手，提示改用 `my_feed`
> 3. `feed` 的 `user_id` 为空 → 直接报错，不再回退到动态流

**幂等保护**：评论前先扫这条说说下已有的评论，如果机器人已经说过一模一样的话，
直接返回「没有重复发」，不调 API、不重复刷屏（LLM 重试也不会刷出一堆重复评论）。

**点赞不背锅**：点赞是附加动作，失败只记一条警告并附注「点赞失败，但评论已发出」，
不会再把已经成功的评论报告成失败（那会导致 LLM 反复重试、重复评论）。

**落地校验（防风控静默吞评论）**：QQ 空间风控会在评论频繁/内容重复时**返回 code=0 成功、
但评论根本不入库**（实测复现：同一段代码，接口全绿，评论列表里永远不出现）。
所以评论发出 3 秒后会**回读目标说说**确认评论真的显示；没出现就返回明确警告
「疑似被风控拦截，请勿重试」，绝不盲目重试刷屏。

> ⚠️ 触发静默禁评后的处理：停掉一切空间评论 12~24 小时让账号冷却，
> 期间继续评论可能加重风控（升级到禁点赞/禁操作）。

## 安装

1. 把整个目录放到 `AstrBot/data/plugins/astrbot_plugin_qzone_pro/`
2. 重启 AstrBot，会自动安装 `requirements.txt` 里的依赖
3. 在插件配置里填：

   - `pro.owner_qq` → 你的 QQ 号
   - `pro.reply_policy` → 先用 `friends`
   - `pro.daily_reply_limit` → 保守一点就从 `10` 开始

4. 在 NapCat / 协议端里登录好 QQ 空间（Cookie 由插件自行维护）

> ⚠️ **必须先停用原版 `astrbot_plugin_qzone`**。两个插件共用同一套登录态，
> 同时开着会互相抢 Cookie、重复评论、重复触发定时任务。

## 已知边界

- 楼中楼只能发现**评论当时就被拉到的**回复。如果对方删了评论，或者说说设了权限，就扫不到。
- 依赖 QQ 空间的非公开接口，QQ 改版可能失效。
- 回复太快容易被风控，`reply_gap_sec` 建议别低于 5 秒。
- 巡检本身不消耗 token，但**每条回复各消耗一次 LLM 调用**，这是唯一的花钱点。

## 字体说明

说说卡片渲染需要一个中文字体。

- **当前使用**：`Noto Sans SC`（SIL Open Font License 1.1，**免费可商用**）
  - 文件：`core/renderer/resources/NotoSansSC-Regular.ttf`（约 2 MB）
  - 许可证全文：`core/renderer/resources/OFL-Noto-Sans-SC.txt`
  - 版权 © 2014–2020 Adobe Systems Incorporated
- **为什么换**：上游原插件附带的是 `汉仪松云朗黑`（**商业字体**），作为公开仓库分发存在
  版权风险。本项目已将其替换为开源字体，仓库中不再包含任何商业字体。
- **想换回自己的字体**：把任意 `.ttf` / `.otf` 放进 `core/renderer/resources/`，
  并修改 `core/renderer/parser_card_renderer.py` 里的 `_FONT_FILENAME` 即可。
